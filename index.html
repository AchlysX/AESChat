How AESChat Works (Under the Hood)

1. The key lives in the link

When a room is created, a fresh 256-bit AES key is packed into the URL fragment (#room=...&key=...). Per RFC 3986, browsers don't send anything after the # in HTTP requests, so the page host (Cloudflare) never receives the key. The trade-off: anyone who has the link has the key and can read the chat — so share it over a trusted channel.

2. Direct Peer-to-Peer (WebRTC)

Message packets aren't relayed through a messaging server or stored in a database — once the connection is up, they flow directly between the two browsers. Setting the connection up does use a signaling server (PeerJS) and STUN servers (Google) to introduce the peers; those see connection metadata, not message content or the key.

3. Authenticated AES-256-GCM Encryption

Every single message generates a fresh 12-byte (96-bit) IV and a 16-byte (128-bit) authentication tag via the browser's hardware-accelerated window.crypto.subtle. If an eavesdropper alters even a single bit in transit, tag authentication fails and decryption rejects the packet instantly.

4. Signal-Style Safety Numbers

A SHA-256 cryptographic fingerprint is derived from the shared key and displayed as 4 clean numeric blocks. Both parties can verify these numbers out-of-band to ensure no Man-in-the-Middle attack is possible.

5. Static hosting, no app server

Unlike a traditional chat that needs a persistent VPS running a socket server, this app is just static files (HTML/CSS/JS) served by Cloudflare, with no backend application to run or maintain. Connection setup still relies on the shared PeerJS and STUN servers described above.
