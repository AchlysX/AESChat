How AESChat Works (Under the Hood)

1. The Zero-Knowledge URL Hash Secret

When an encrypted room is generated, the 256-bit AES key is packed into the URL fragment (#room=...&key=...). According to the RFC 3986 HTTP specification, browsers never send anything after the # in HTTP requests. Cloudflare's servers never see or log the encryption key.

2. Direct Peer-to-Peer (WebRTC)

Messages never pass through an intermediate messaging server or database. Once WebRTC signaling completes, packets flow directly between the two browser devices across Google STUN relays with sub-50ms latency.

3. Authenticated AES-256-GCM Encryption

Every single message generates a fresh 12-byte (96-bit) IV and a 16-byte (128-bit) authentication tag via the browser's hardware-accelerated window.crypto.subtle. If an eavesdropper alters even a single bit in transit, tag authentication fails and decryption rejects the packet instantly.

4. Signal-Style Safety Numbers

A SHA-256 cryptographic fingerprint is derived from the shared key and displayed as 4 clean numeric blocks. Both parties can verify these numbers out-of-band to ensure no Man-in-the-Middle attack is possible.

5. Serverless & $0 Forever

Unlike traditional chat servers that require a persistent VPS running a C/Node socket server, this entire architecture deploys as static assets on Cloudflare Pages with zero maintenance and zero hosting fees.
